# スキル改訂 適用手順（release-gate / adversarial-review）

2026-07-29。人件費シミュレーター v0.5 の作業で判明した抜けを塞ぐ。

## なぜ改訂するか

release-gate を5回通したが、**画面上の矛盾は1件も捕まらなかった。**
10件以上すべて水田さんの目視で発見されている。

| 検査 | 見つけた件数 |
|---|---|
| 水田さんの目視 | 10件以上 |
| release-gate（5回） | 0件 |
| 機械テスト | 指摘後に固定した分のみ |

release-gate は「制度適合・誤回答・ブランド毀損」の観点で見るため、
**同じ画面の2つの表示が食い違う**という型は守備範囲外だった。
観点を足すのではなく、**検査の種類を足す**必要がある。

---

# 改訂1：release-gate に STAGE 1.6 を追加

`/mnt/skills/user/release-gate/SKILL.md` の
**STAGE 1.5 の直後、STAGE 2 の直前**に以下を挿入する。

---

```markdown
### STAGE 1.6：画面整合の機械検査（2026-07-29追加・教訓E-015/E-016）

**画面に出る主張どうしが矛盾していないかを機械で確認する。目視は検査ではない。**

観点レビュー（STAGE 2）は「制度に照らして正しいか」を見る。
このステージは「同じ画面の2つの表示が違うことを言っていないか」を見る。
別の検査であり、STAGE 2 では代替できない。

#### 1.6-1 主張の列挙

画面に出る「主張」を列挙する。主張とは真偽で答えられる表示のこと。

- 基準を満たす／満たさない
- 区間・範囲がある／ない
- 不足がある／ない
- 警告色である／ない
- 要素が表示される／されない

列挙は計算層（engine）の返り値から機械的に導出する。
**UI層で判定している主張があれば、その時点でP1指摘**（同じ判断を2か所で
計算しているため、必ずいつかずれる）。

#### 1.6-2 主張どうしの整合

列挙した主張について、矛盾する対を定義し検証する。

| 例 | 整合条件 |
|---|---|
| 成立区間 | 区間がある ⟺ 帯・範囲が描画される |
| 充足判定 | 充足している ⟺ 不足リストが空 |
| 比率表示 | 比率が基準内 ⟺ 警告色でない |
| 合計と内訳 | 内訳の和 ＝ 合計（表示上の丸め後も） |

#### 1.6-3 網羅性

engine が返す主張のうち、1.6-2 で突き合わせていないものを検出する。
**列挙漏れ自体を機械が指摘できること。**

人が列挙してから網を張る限り、列挙漏れは必ず残る。
気づいていない要素はいつまでも検証されない（E-016）。

#### 1.6-4 走査範囲

代表的な入力パターン（全サービス種別 × 境界値 × 偏った構成）で
全主張を走査し、矛盾する組み合わせが0件であること。

**端点は「連続で」踏むこと。**1回踏むだけでは発散しない不具合がある
（ランダム探索1万件が見逃した実例あり）。

#### 1.6-5 実ピクセル

文字の欠け・はみ出しは jsdom では検出できない。
ヘッドレスブラウザで実ピクセルを測る。複数幅＋モバイル。

判定条件：
- 各セル・ラベルで `scrollWidth <= clientWidth`
- `document.documentElement.scrollWidth <= window.innerWidth`
- 主要な数値表示に NaN / undefined / Infinity が出ていないこと

#### 1.6-6 テストの偽陰性チェック（教訓E-018）

回帰テストが**修正前のコードにも存在する手がかり**で書かれているか確認する。

- 修正時に新設した属性・クラス・IDを条件にしていないか
- 「要素が見つからない」で合格していないか
- 対象範囲が広すぎて、別の箇所の同じ記述で通っていないか
- fail-before の失敗メッセージが**意図した理由**か
  （「属性がない」で落ちているなら意図した検証ではない）

**このステージが通らなければ STAGE 2 に進まない。**
```

# 改訂2：release-gate に STAGE 0.5 を追加

**STAGE 0 の直後、STAGE 1 の直前**に以下を挿入する。

---

```markdown
### STAGE 0.5：指示の消化確認（2026-07-29追加）

release-gate は品質の観点でレビューするが、
**「依頼されたことが全部入っているか」は見ていない。** 別の検査である。

`docs/指示台帳.md` と実装を突き合わせ、未消化の項目がないことを確認する。
台帳がなければ作る。未消化があれば gate に進まない。

台帳の列：ID / 内容 / 指示日 / 状態（未着手・実装済み・利用者確認済み）/ コミット

**背景**：v0.5 の作業で、指示の抜けを水田さんが4回指摘した。
指示の管理が担当者の記憶に依存していたことが原因。
```

# 改訂3：release-gate の STAGE 2 に観点⑧を追加

STAGE 2 の観点表に1行追加する。

---

```markdown
| ⑧ 説明と実装の一致 | 計算式・定義を変えたとき、その式を説明している文章が追随しているか（E-014） |
```

あわせて、STAGE 2 の直前に以下の手順を追記する。

```markdown
**観点⑧の走査手順（E-014）**

計算式・定義・分母を変更した場合、その式を説明している文章をすべて洗い出す。

1. 変更前に**日本語の言い回しを指紋として列挙**する（変数名だけでは足りない）
2. 全ファイルを grep で走査。対象に次を明記：
   入力欄のhint／凡例／グラフ内注記／SVGのaria-label／免責一文／
   書き出しテキスト／README／設計書／コード内コメント
3. ヒットを ①要修正 ②履歴（枠で明示） ③無関係 に3分類
4. **走査結果をレビュー報告に貼る。貼っていなければ未実施とみなす**

同じ型の見落としを1日で3回繰り返した実例がある
（§5/§6の表示条件、READMEの旧係数、職種表の注記）。
```

# 改訂4：adversarial-review モード2に観点を追加

`/mnt/skills/user/adversarial-review/SKILL.md` の
**「対象の種類（2モード）」のモード2の説明**に、以下の観点を追加する。

---

```markdown
モード2で必ず含める観点（2026-07-29追加）：

- **同じ判断が2か所で計算されていないか**
  UI層に判定式が書かれていないか。同じ量を別の変数で持っていないか
- **画面に出る主張のうち、テストで突き合わせていないものはないか**
  指摘された箇所だけに網を張ると、列挙漏れが残り続ける
- **計算の正しさと操作感が衝突していないか**
  判断の基準となる要素（帯・線・軸）が、操作で動いていないか。
  基準が動くと道具として使えなくなる（E-017）
- **実装からの「確認が要る」という申し送りを、計算の正しさだけで処理していないか**
```
