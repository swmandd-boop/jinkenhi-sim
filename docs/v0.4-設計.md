# v0.4 設計 — 賃金入力の削減と診断機能

2026-07-27 作成。v0.3 に対する変更仕様。実装は Claude Code が行う。

## 背景

このツールはウェブ上で動き、入力は保存されない。したがって入力の量は
そのまま「使われなさ」に直結する。この観点で職種別の基準年収を検証したところ、
**集計値に一切影響していないことが確認できた**。

| 職種別の基準年収 | 平均年収 | 人件費率 | 人件費総額 | 正規平均 | 非正規平均 |
|---|---|---|---|---|---|
| 既定（施設長600・介護370…） | 665.23 | 64.30% | 23,792 | 731.03 | 511.72 |
| 全職種フラット400 | 665.23 | 64.30% | 23,792 | 731.03 | 511.72 |
| 極端な格差（1500/250） | 665.23 | 64.30% | 23,792 | 731.03 | 511.72 |

原資は「収益 × 人件費率」で決まり、平均年収は「原資 ÷ 人数」で決まる。
職種間の配分をどう変えても総額は動かない。これはこのツールの主題そのものであり、
主題と無関係な入力を10行ぶん求めていたことになる。

## 1. 削除するもの

- `rows[].a`（職種別の基準年収）と、その入力列
- 賃金倍率 `k`、および `Bs` / `Bh`
- 「入力した基準年収どおりにする」ボタン（`fit-wage`）
- 表の「基準年収」「正規年収」「非正規年収」の3列
- テスト `INV-08`（非正規年収＝正規年収×水準）、`INV-09`（倍率1.000）

副次的に、敵対的レビュー指摘④「fit-wage が ×1.000 表示なのに実倍率 0.99959」は
機能ごと消滅する。個別の修正は不要。

## 2. 計算の再定義

`hw = 非正規の賃金水準 ÷ 100` として、

```
pool  = total / (1 + fuku/100)
avg   = pool / n
avgSe = pool / (nSe + hw * nHi)
avgHi = avgSe * hw
```

v0.3 の結果と完全に一致することを確認済み（hw = 0 / 0.5 / 0.7 / 1.0 / 1.3、
scale = 1.3 で小数第4位まで一致）。

**恒等式**（新しい不変条件にする）:
`nSe * avgSe + nHi * avgHi = pool`

## 3. 表の構成

残すのは職種別の**人数**のみ。3:1 や看護職員の段階配置は職種別の要件であり、
ここを畳むと「合計で判定して職種別を見落とす」バグに戻る。

```
職種 | 基準 | 正規 | 非正規 | 合計
```

## 4. 入力の全体像

```
STEP1  サービス種別・定員・稼働率
STEP2  収益（規模から概算）／人件費率／法定福利費率／賞与月数
STEP3  職種別の人数（正規・非正規）
STEP4  非正規の賃金水準／配置の下限／下回れない平均年収／人件費の年間上昇率
```

## 5. 新機能A — 必要人件費率

「譲れない線を守るのに必要な人件費率」を1つの数字に集約する。
計算自体は v0.3 の verdict 内に既にあるものを前面に出す。

```
needTotal = nmin * atgt * (1 + fuku/100)
needRatio = needTotal / rev * 100
gapPt     = needRatio - effRatio
```

**閾値は設けない。**符号だけで分岐する。

**表示条件（2026-07-27 追記）：`atgt` が初期値のまま（未入力）の場合は必要人件費率の
数値を出さず、§6 と同じく「下回れない平均年収を入れてください」と促す。**
必要人件費率は `nmin × atgt` で計算するため、初期値400万のままだとサンプル値を根拠にした
診断結果が出てしまう。§6 の賃金側を伏せた理由（初期値400万はサンプルで、これを基準に
診断すると未検証の値が判定基準になる）がそのまま §5 にも当てはまる。§5 と §6 で
片方だけ数値が出る状態を作らない（回帰テスト UI-09）。

- `gapPt <= 0` → 人件費の内側に余地がある。増員と賃上げのどちらに回すかの判断
- `gapPt > 0` → 不足。不足分を次の2つに換算して示す
  - 収入をいくら増やす必要があるか: `needTotal / (ratio/100) - rev`
  - 常勤換算を何人減らす必要があるか: `n - pool/atgt`

`gapPt > 0` のときの文言に、次の一文を含める。

> ここから先は人件費の内側では解けません。収入を増やすか、人件費以外の費用を
> 見直すかのどちらかになります。

**稼働率の扱い**: 職員配置と賃金水準が動かなければ人件費総額は動かない。
稼働率が変わると収入（分母）だけが動き、率が上下する。
稼働率を下げたときに人件費率がどう動くかは、STEP1の稼働率を操作すれば見える。
損益分岐稼働率は算出しない（人件費以外の費用が必要になるため、このツールの範囲外）。

## 6. 新機能B — 定点の位置づけ

**閾値を発明しないため、象限判定ではなく2つの「余裕」で表す。**

```
配置の余裕 = n - nMinComp        （人。職種別基準を満たす最小合計との差）
賃金の余裕 = avg / atgt          （倍）
```

原点はいずれも法人側が決めた線（配置は法令基準、賃金は入力値）であり、
こちらが基準値を発明していない。

表示の条件:

- **`atgt` が初期値のまま（未入力）の場合は賃金側の判定を出さない。**
  「下回れない平均年収を入れてください」と促す。
  初期値400万はサンプルであり、これを基準に診断すると未検証の値が
  判定基準として機能してしまう。
- **配置の余裕がほぼゼロ（`|n - nMinComp| < 0.5`）の場合**は次を表示する。

  > 配置が基準ちょうどです。休暇・欠員・夜勤の変動を吸収する余地がありません。
  > 実際の配置人数を入れて確かめてください。

  これが敵対的レビュー指摘②「起動直後の平均年収665万円の独り歩き」への対処。
  注記を足すのではなく、その状態を診断が名指しする。

## 7. 新機能C — 推移

定点（直近決算）から、**現行の賃金カーブを維持した場合**の人件費率の推移を出す。

入力は1つ。`g` = 常勤換算1人あたり人件費の年間上昇率（％）。

```
人件費率(t) = effRatio * (1+g)^t
人件費増分(t) = total * ((1+g)^t - 1)
```

**既定値は 0.0％** とする。0％なら推移は平坦になり、何も主張しない。
入力して初めて動く。既定値を置くと、それが未検証のサンプルとして
将来予測の顔をしてしまうため。

入力欄には次の導き方を併記する。

> 2期分の決算から「人件費総額 ÷ 常勤換算数」の伸び率を計算してください。
> 定期昇給・昇格に加えて、退職と新規採用による入れ替えの効果も含んだ実績値になります。

表示は 3年後・5年後・10年後の3点。加えて、増分を吸収する3択を出す
（既存の「限界トレードオフ」と同じ形式）。

```
5年後の増分 X万円 を吸収するには
  収入を増やす      : +Y万円（年率 Z%）
  常勤換算を減らす  : -W人
  昇給カーブを抑える: g を下げる
```

**織り込まないこと（明示する）**

- 介護報酬改定（3年ごと・予測不能）。収入横ばいは悲観シナリオではなく
  「制度を変えなければこうなる」という基準線であり、報酬改定分は安全余裕になる
- 処遇改善加算の改定
- 稼働率の将来変動（人口動態は別ツールの領分）

## 8. 追加する不変条件テスト

| # | 内容 | 由来 |
|---|---|---|
| INV-15 | `nSe*avgSe + nHi*avgHi = pool` | 新式の恒等式 |
| INV-16 | `avgHi = avgSe * hw` | 同上 |
| INV-17 | **`scale ≠ 1` でも 正規計＋非正規計＝合計** | 敵対的レビュー指摘⑤。v0.3 の UI-01 は scale=1 でしか検証していなかった |
| INV-18 | `gapPt <= 0` ⇔ `feasible` | 必要人件費率と成立判定の整合 |
| INV-19 | `g = 0` なら全年次で人件費率が定点と一致 | 推移 |
| INV-20 | 推移の3択がいずれも同じ増分を指す（下記の注意を参照） | 推移 |
| INV-21 | 職種別人数を固定したまま他の入力を変えても `nMinComp` は不変 | 配置基準 |

**INV-17 について。** v0.3 の UI-01 は「実バグの回帰テスト」としながら
`scale = 1` の1点でしか検証しておらず、スライダー操作時の不整合を捕らえられなかった。
新規テストは `scale` を 0.4 / 0.7 / 1.0 / 1.3 / 1.8 で回すこと。

**INV-20 について（設計時に一度誤った箇所）。** 人数削減による吸収を検算するとき、
掛ける単価は**現在時点ではなく t 年後の1人あたり人件費**である。

```
削減人数     = n * (1 - 1/(1+g)^t)
t年後の単価  = (total / n) * (1+g)^t
削減人数 × t年後の単価 = 増分
```

現在時点の単価で検算すると 2,476万に対して 2,243万となり一致しない。
テストでは t 年後の単価を使うこと。

v0.4 に入る前に、敵対的レビューの指摘のうち次の2件を済ませておく。

- **⑤ スライダー操作時の `正規計＋非正規計 ≠ 合計`**

  常勤換算の粒度として許容範囲と判断する。

  判定キーを実利用者数 `u` から入所定員 `sz.cap` に変更する。
  基準の文言「入所定員100以上で1以上」と一致させる。

## 11. STEP2「原資を決める」の作り直し（2026-07-27 追記）

### 背景（作り直しの理由）
旧 STEP2 は「収益 × 人件費率 = 人件費総額」の向きで、人件費率が入力だった。その結果、
下部の「実質人件費率」が入力値をそのまま返す循環になっていた（入力64.3 → 表示64.3％）。
決算書には収益と人件費総額の両方が実額であるので、率は割り算で出せる。そうすれば人件費率は
法人の実績値になり、全サービス平均64.3％との比較が診断として成立する。

### 入力（2つだけ・どちらも「決算書から転記」）
- 年間サービス活動収益（万円）
- 年間人件費総額・法定福利費込み（万円）

### 削除
- 入所者1人1日あたり収入の入力欄と `priceBasis` / `unitPrice` / `annualDays`（＋ `annualMult`）
- 「STEP1の規模から収益を概算する」チェックボックスと `autoRev`
- 人件費率の入力欄
- 「収益×人件費率」／「人件費総額を直接」のモード切替（`mode`）

### 出力に回す
- 人件費率 ＝ 人件費総額 ÷ 収益（`effRatio`）。参考値64.3％を併記
- 1人1日あたり収入 ＝ 収益 ÷ 利用者数 ÷ 年間稼働日数（`unitRev`。円/人/日）。水準の良し悪しは
  判定しない。年間稼働日数は入所系365・通所は営業日数×52（`opDaysOf`。出力専用に残す）

### 追加する一文
定員・稼働率の入力欄の近くに「定員や稼働率を変えたときは、年間サービス活動収益も見直して
ください（収益は決算書の実額で、規模に自動連動しない）」。

### テスト
- 新設 STEP2-01（人件費率 ＝ 人件費総額 ÷ 収益）／STEP2-02（収益0で率・単価が NaN/∞ にならない）
- 整理: INV-13（自動計算時は規模と収益が連動）と UI-04（規模連動中は収益欄が読み取り専用）を
  削除。INV-18 は `ratio` ではなく `total` を振って effRatio を変える形に書き換え。
  explore の randomInput から mode/autoRev/price/ratio を除去。dump の mode/price 依存シーンを差し替え。
